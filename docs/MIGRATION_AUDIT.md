# Nuvik Vet — Inherited Migration Audit

## Scope and safety

Reviewed every SQL file currently in `server/migrations` (001–011), the migration invocation paths in Compose/package scripts, `server/apply-migration.cjs`, and the development seed script. No SQL was executed; no migration was edited, deleted, or reordered; no database was contacted. This is a source review, not a live-schema inspection.

The Compose PostgreSQL init-directory mount has been removed so a fresh Nuvik database cannot silently execute this inherited Human Clinic migration chain. The existing SQL files remain unchanged as historical reference. Do not mount them back or run `server/apply-migration.cjs` for Nuvik.

### Additional detail on core inherited columns

- `patients` is a human being with Arabic male/female sex, blood type, chronic disease and emergency-contact fields. It cannot be repurposed as an animal table without breaking meaning and validation. No owner/customer entity exists, and one owner with multiple animals cannot be represented correctly.
- `visits.weight`, `temperature`, `heart_rate`, `blood_pressure`, and `height` are text fields rather than typed dated measurements. They do not provide animal-specific units, body-condition history, species context or consultation-level observations.
- `prescriptions.medications` is JSONB and `visits.medications` is free text. Neither has normalized prescription lines, dispensing status, lot linkage, product linkage or stock effects. No inventory entities exist.
- `appointments` references `patients` and `users` directly and has date/time columns without branch/timezone or overlap protection. There is no boarding or accommodation booking model.
- `users.role` is constrained to `reception` or `doctor`; no role/permission tables, clinic membership, branch membership or employee profile exists.
- Invoice lines reference clinic `services`, not products, boarding reservations, consultations or department/source events. There is no sales/return, purchase/supplier, stock movement, product/barcode, batch/expiry, tax jurisdiction or payment-allocation entity.
- `financial_audit_logs` only covers finance route behavior and stores polymorphic entity IDs without an FK; there is no general `audit_events` table or tenant/branch scope.

### Migration 011 financial column and relationship inventory

- `service_categories`: ID, unique name, active flag, created/updated times. `services`: name/code, optional category, description, numeric price, active flag, creator and timestamps.
- `invoices`: unique invoice number; required patient; optional visit/doctor; invoice/due dates; subtotal, discount type/value/amount/reason, tax, total, paid/remaining amounts, status, notes, creator/updater and timestamps. `invoice_items`: required invoice, optional service, service name/code snapshots, quantity, unit price, line total and timestamp.
- `payments`: required invoice, positive amount, method, optional reference/notes, receiver and payment/creation times. `refunds`: invoice and original payment, positive amount, required reason, creator and timestamp. No unique idempotency key or payment-allocation table is defined in this migration.
- `expense_categories`: unique name/active/created. `expenses`: optional category, positive amount/date/method/description/notes/receipt path, creator/updater and timestamps.
- `commission_rules`: required doctor, optional service, percentage/fixed type, nonnegative value, active/creator/timestamps. `doctor_commissions`: invoice item, doctor, nonnegative amount and optional rule. `cashier_closings`: unique date, opening/expected/actual cash, notes and closer. `financial_audit_logs`: entity type/UUID/action/JSON details/actor/time.
- No checks reconcile invoice items with invoice totals, payments/refunds with paid/remaining amounts, refunds with net captured value, or commissions with source rules. The migration creates an invoice-number sequence but no column default/trigger; application code supplies invoice numbers.

## Triggers, functions, and seed data

No migration defines a custom SQL function or trigger. The only function-like dependency is the `pgcrypto` extension's UUID generator in 001; modern PostgreSQL deployments should decide whether to rely on built-in UUID generation or explicitly manage extensions.

Data writes inside migrations are not limited to schema: 004 backfills human patient/provider assignments; 006 inserts human investigation reference rows; 008 inserts more human tests/imaging. Outside migrations, `server/src/seed.ts` inserts a reception account, seven human doctors, a hard-coded demo password, and three sample human patients. It is not called by Compose, but must not be used as a Nuvik or production seed. Use synthetic veterinary fixtures and a one-time secure administrator invitation instead.

## Ordering and migration risks

The implicit order is lexical 001→011. Dependencies include 002/003/004/005/006/007/009/011 on 001; 004 on queue, visits, prescriptions, prescription images and appointments; 007 on queue, patient investigations and attachments; 008 on `investigation_types` from 006; 009 on users and queue. 010 assumes `patients.status` exists. 011 assumes users/patients/visits already exist.

The chain has no migration ledger, checksums, rollback scripts or lock. Most `CREATE TABLE/INDEX` statements use `IF NOT EXISTS`, but that does not prove an existing object has the expected definition. Migration 005 unconditionally drops a named constraint. Migration 010 drops data. Migration 011 creates tables/sequences without `IF NOT EXISTS`. Compose previously mounted the directory into the Postgres image init hook, which only runs on an empty data directory and can fail partway through initialization; later file changes would not be a reliable upgrade mechanism. `server/apply-migration.cjs` is a one-off hard-coded runner for 010, not a general migration system.

## Recommended clean Nuvik migration strategy

1. Keep the inherited `server/migrations` directory unchanged as read-only historical reference; do not mount it into Nuvik PostgreSQL or run it.
2. Use the Nuvik-only `db/migrations/` directory with Flyway Community for explicitly run, ordered versioned SQL migrations. Flyway owns `flyway_schema_history` and validates checksums; do not create an application `schema_migrations` table. PostgreSQL initialization and ordinary API startup must not run migrations.
3. V001 is the implemented empty-database foundation: `clinics`, `branches`, `users`, `roles`, `permissions`, `role_permissions`, `user_roles`, and `audit_events`. Roles and grants are clinic-level with no `branch_id`; the permission catalog is installation-wide. It includes `clinics.settings.allow_negative_stock`, `clinics.invoice_number_counter`, `btree_gist`, and audit triggers that reject row UPDATE/DELETE and statement TRUNCATE; `audit_events.actor_id` is nullable while its clinic and branch are required. Flyway owns `flyway_schema_history`; V001 inserts no seed rows and creates no database roles or credentials. Then add customer/animal/species/breed and ownership; next clinical encounters/diagnoses/prescriptions/vaccines; then separately boarding and hospitalization; then catalog/inventory and purchasing/sales; then unified invoices, payments, refunds and expenses.
4. Follow the MVP scope: operational rows carry `clinic_id` and relevant branch-scoped rows carry `branch_id`; roles and grants are clinic-level, and this MVP does not implement composite tenant foreign keys or RLS. Keep one client per database. Before any SaaS or shared-database deployment, add and test cross-tenant composite constraints or equivalent protections. Use restrictive deletion for clinical, financial, stock and audit history, and keep migration-owner credentials separate from the least-privilege runtime API role.
5. Keep seeds separate from schema. Seed only public reference data and synthetic test fixtures; create initial administrators through a secure invitation/secret flow. Never seed a universal password or real client records.
6. Review each migration against the ER design, run migration tests only against an isolated disposable Nuvik database, verify a new database from zero, and verify upgrade/restore procedures before any controlled first application startup.

### Refined design baseline

The exact first-migration scope in `docs/MVP_DATABASE_DESIGN.md` is implemented by `db/migrations/V001__foundation.sql`: clinics, branches, users, clinic-level roles and grants, installation-wide permissions, and minimal audit events. It has no customer/animal, clinical, boarding, inventory, or finance tables, and no seed data or database-role creation. Flyway Community is selected; its own `flyway_schema_history` and versioned migration checksums replace the proposed application migration ledger. On disposable PostgreSQL 16.15 with Flyway 13.11.1, tests verified applying V001 to an empty database, a no-op rerun, checksum-tamper rejection, rollback of a deliberately failed migration, and successful `btree_gist` creation by a non-superuser database owner. Concurrent migration locking in practice and the migration method available on the client Windows PC (Docker or standalone Flyway CLI) remain unverified. Neither PostgreSQL initialization nor ordinary API startup may run migrations automatically.

The refined ownership model has `animal_owners` as the sole source of truth; it explicitly rejects the earlier duplicate `animals.primary_owner_id` possibility. See `docs/DATABASE_DECISIONS.md` for product and operations decisions still open before schema implementation.

## Startup blocker

V001 and the Flyway workflow have been implemented and tested on a disposable PostgreSQL 16.15 database. Do not treat the application as ready for first startup: later domain tables and the separate reviewed clinic/branch/administrator bootstrap remain outstanding. PostgreSQL initialization and API startup must not apply migrations automatically; any first application startup requires an explicit controlled migration and bootstrap procedure.
